     中間是版本號，人看得懂；

     所以我要退回舊版，就是指定這一串。」

 ---- 分頁5  ECS 服務 ----

 畫面上要指的地方：  Tasks (2 Desired)  2 running | 0 pending

 說：
   「這裡同時跑著兩份我的程式。
     換版的時候，先把新的開起來、確認健康了，才關掉舊的，
     所以中間服務不會斷。
     我實測過部署期間打 300 次請求，300 次全部成功。」

 如果老師問「那個 task:19 是什麼」：

   「那是第 19 版設定檔。代表這套服務被重新部署過 19 次，
     每一次都是機器做的，我沒有手動改過任何一次。」


 ---- 分頁6  EC2 機器 ----   ★ 這頁最能講安全

 動作：點中間的「Security」頁籤，往下捲到 Inbound rules

 畫面上只有一條規則：  Port 80 / TCP

 說：
   「這台機器的防火牆規則只有一條，就是 80 port，也就是網頁。
     沒有 22，代表誰都不能 SSH 連進來——包括我自己。
     我也沒有建任何金鑰。

     那怎麼部署？靠 AWS 的 Systems Manager，
     是機器主動向外跟 AWS 拿指令，不是外面連進來，所以門不用開。

     在金融業，金鑰外流和特權帳號被盜用是稽核最常問的兩件事。
     這個做法讓這兩個風險根本不存在——
     不是把鑰匙管好，是根本沒有鑰匙。」

 如果老師問「那機器怎麼有權限拉映像檔」：

   「靠上面那個 nkc202-cicd-ec2-role 角色。
     權限只給兩項——讀 ECR、接 Systems Manager 指令，其他都不能做。
     這是最小權限原則。」


 ---- 分頁7  CloudFormation ----

 畫面上：兩個堆疊，都是綠色的 CREATE_COMPLETE

   nkc202-cicd-base  = 地基（VPC、子網路、防火牆、EC2、IAM）
   nkc202-cicd-ecs   = 上層（負載平衡器、ECS 叢集、任務定義）

 說：
   「剛才看的那三頁，全部是從這兩個檔案長出來的。
     我沒有在 console 上一個一個點按鈕，我寫了兩個 YAML 交給 AWS，
     它自己蓋好。這叫基礎設施即程式碼。

     所以環境如果被誤刪、或要在另一個帳號重建一份一樣的，
     我不用記得當初點了哪四十個按鈕，把檔案再跑一次就好。

     而且這兩個檔案在 GitHub 上，誰改過哪一行都查得到。
     對金融業來說這就是變更管理——留軌跡，不靠某個人的記憶。」

 註：Description 欄位如果顯示成一堆問號，那是字型問題不是壞掉，
     講堆疊名稱和綠色狀態就好，不用點開。

                     用分頁1到3 照樣可以完成 Demo

 完全跑不動       → 翻報告第三章，數據和截圖都在
