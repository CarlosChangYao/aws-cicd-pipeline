##############  Demo 正片（約 4 分鐘）  ##############

  主線＝故事 1「黑天鵝・緊急調降風控參數」
  另外兩個故事在後面，時間夠或老師想再看一次時用。


================================================================
  第 1 步：講情境（30 秒。這 30 秒決定整場的高度，不要跳過）
================================================================

 動作：切到「分頁1」，重新整理

 說：
   「剛才簡報講的是我把部署從 18 步、16 分鐘，做到 1 步、80 秒。
     現在我給大家看，這件事在券商實際上長什麼樣。

     這是一個定期定額試算頁。
     大家注意最下面這一列——單筆委託上限，現在是 50 萬。

     假設今天盤中突然出現極端行情。
     風控單位下令：立刻把單筆委託上限從 50 萬調降到 10 萬，控制曝險。

     這件事在程式上只是改一個數字。
     但傳統流程要開緊急變更單、找主管簽核、排上線窗口、
     通知 IT 值班、通知業務單位待命——盤中根本來不及，
     最快是收盤後，甚至隔天。

     風險敞開的那段時間，就是實際的損失。

     我現在用這條流水線做一次。」


 ※ 如果老師追問「你們會在盤中改程式？」——這句話要答得出來：

   「調的是風控參數，不是交易邏輯。
     風控參數本來就是設計成要能緊急調整的。
     重點是，過去『能不能快速調整』受限於部署流程；
     現在部署不再是瓶頸了。」


================================================================
  第 2 步：改程式（貼一行）
================================================================

 貼：

bash 現場調風控.sh

 畫面會印出改了哪一行、還有新的風控狀態。指著它說：

 說：
   「就這一行，50 萬改成 10 萬。」


================================================================
  第 3 步：送出（今天唯一的人工動作）
================================================================

 貼：

git add -A && git commit -m "風控緊急調降單筆委託上限至 10 萬" && git push origin main

 說：
   「我按下送出。
     從現在到新參數上線為止，我不會再碰任何東西。
     特別強調一件事——我不會登入 AWS。
     AWS 上的機器、網路、負載平衡器，我一根手指都不會碰。」


================================================================
  第 4 步：切到分頁2，看機器自己跑
================================================================

 動作：切到「分頁2」(GitHub Actions)，看四個階段依序變綠

 說：
   「機器現在自己在做四件事：
     第一，跑測試——測試不過的話，後面三個完全不會執行。
     第二，把程式打包成映像檔，推到 AWS 的倉庫。
     第三跟第四，同時部署到兩台不同的機器。」

 多講一句（測試在守什麼，這段很加分）：

   「我的測試裡有一條是風控規則：
     現行委託上限，不得高於平時上限。

     萬一有人把 10 萬誤打成 100 萬——多打一個零——
     那等於偷偷把風險敞口放大，而且沒有人會發現。
     這條測試會直接把它擋在上線之前。

     以前這種事靠人工複核、靠主管簽核時眼睛夠不夠尖。
     現在是機器強制執行，繞不過去。」


================================================================
  第 5 步：★ 切到分頁3，看 AWS 上自己長出新版本
================================================================
  這是老師要看的「開 AWS」。等待的時間都花在這裡。

 動作：切到「分頁3」(ECR)，一直按重新整理

 大約 60 秒後畫面會變：

     Images (n)  -->  Images (n+1)      數字自己加一
     最上面多出一列，時間是今天，標籤是剛才那次 commit 的編號

 說：
   「這是 AWS 上的映像檔倉庫。
     我從按下送出到現在，完全沒有碰 AWS。
     這個新版本是流水線自己推上來的。」

 指著最上面那一列的三個標籤：

   「一個映像檔掛了三個標籤。
     latest 是最新的，但下一次建置就會被搶走；
     中間是版本號，給人看的；
     最後這一串是 commit 編號，永遠不會被蓋掉。
     萬一這次調整調錯了要退回去，指定的就是這一串。」


================================================================
  第 6 步：回分頁1，收尾（整場的重點，慢慢講）
================================================================

 動作：切到「分頁1」，按重新整理

    畫面會有三個變化，一起發生：

      單筆委託上限   NT$ 500,000  -->  NT$ 100,000
      顏色           藍           -->  紅
      並且出現       ⚠ 風控加強中 的紅色標籤
      整張卡片外框                -->  變紅

 說：
   「參數生效了。
     而且大家注意——變紅的不只是數字，還有標籤跟整個外框。

     這不是我改了三段文字。
     我只改了一個數字，程式自己判斷『現行上限低於平時水準』，
     所以整個頁面進入警戒狀態。這是邏輯，不是文案。」

 貼（對照用）：

git log --oneline -1

 說：
   「網頁上顯示的 commit 編號，跟我電腦裡的完全一樣。
     所以線上現在跑的是哪一版風控參數，是百分之百確定的。
     這在金融業叫可追溯性，稽核一定會問。」

 ★★ 最後這段是結論 ★★

   「回到一開始的情境。

     用傳統流程，這個風控調整最快是收盤後，甚至隔天。
     中間那幾個小時，風險是敞著的。

     剛才這一次，從我按下送出到生效，不到兩分鐘，一個人，
     而且是盤中就能做，因為換版的時候服務不會中斷。

     對券商來說，這不只是部署變快。
     是把作業風險、法遵回應時間、還有風控措施的生效速度，
     一起壓下來。」


================================================================
  故事 2（備案）：主管機關要求加註風險警語
================================================================
  流程完全一樣，只把第 2 步的指令換成：

bash 現場改警語.sh

 情境台詞：
   「假設今天主管機關發函，要求所有投資試算頁面
     都必須加註風險警語，明天生效。」

 上線後會多出一塊橘黃色的警語框。

 收尾台詞：
   「一行警語，傳統流程要等一天。剛才不到兩分鐘。
     這就是法遵回應時間。」


================================================================
  故事 3（備案）：業務單位調整手續費優惠
================================================================
  流程完全一樣，只把第 2 步的指令換成：

bash 現場改費率.sh

 情境台詞：
   「業務單位要打促銷，定期定額手續費優惠從 6 折調到 5 折。」

 上線後：優惠折扣 6 折 → 5 折，每次手續費 NT$ 9 → NT$ 7。


##############  被問到才開的三頁  ##############


 ---- 問「怎麼做到不斷線」 → 開 ECS ----

 https://ap-northeast-1.console.aws.amazon.com/ecs/v2/clusters/nkc202-cicd-cluster/services/nkc202-cicd-service/health?region=ap-northeast-1

 指著：  Tasks (2 Desired)   2 running | 0 pending

 說：
   「這裡同時跑著兩份我的程式。
     換版時先把新的開起來、確認健康了，才關掉舊的。
     中間永遠有人在服務，所以不會斷。
     我實測過部署期間打 300 次請求，300 次全部成功。」


 ---- 問「安全怎麼做」 → 開 EC2 ----   ★ 這頁最強

 https://ap-northeast-1.console.aws.amazon.com/ec2/home?region=ap-northeast-1#InstanceDetails:instanceId=i-0937ad0e32c5fedca

 動作：點中間的「Security」頁籤，往下捲到 Inbound rules
 畫面上只有一條：  Port 80 / TCP

 說：
   「這台機器的防火牆只有一條規則，80 port，也就是網頁。
     沒有 22，代表誰都不能 SSH 連進來——包括我自己。
     我也沒有建任何金鑰。

     那怎麼部署？靠 AWS 的 Systems Manager，
     是機器主動向外拿指令，不是外面連進來，所以門不用開。

     金鑰外流和特權帳號被盜用，是金融業稽核最常問的兩件事。
     這個做法讓這兩個風險根本不存在——
     不是把鑰匙管好，是根本沒有鑰匙。」


 ---- 問「環境怎麼建的」 → 開 CloudFormation ----

 https://ap-northeast-1.console.aws.amazon.com/cloudformation/home?region=ap-northeast-1#/stacks

 畫面上：兩個堆疊，都是綠色 CREATE_COMPLETE

   nkc202-cicd-base  = 地基（VPC、子網路、防火牆、EC2、IAM）19 個資源
   nkc202-cicd-ecs   = 上層（負載平衡器、ECS、任務定義）  12 個資源

 說：
   「這兩個檔案總共建了 31 個資源。
     我沒有在 console 上一個一個點，我寫了兩個 YAML 交給 AWS。
     這叫基礎設施即程式碼。

     我刻意拆成兩個：地基幾乎不會動，動了就是大事；上層常常要調。
     分開之後改上層完全碰不到地基，爆炸半徑小。

     而且檔案在 GitHub 上，誰改過哪一行都查得到。
     對金融業來說這就是變更管理。」


 ---- 問「這樣要花多少錢」 ----

 說：
   「開發階段幾乎都在免費額度內。
     目前主要成本是負載平衡器和 Fargate，一天大約 1.3 美元。
     我有設預算告警，驗收後會把資源全部清掉。」


 ---- 問「為什麼沒做關 5（跨雲）」 ----

 說：
   「我評估過。要另外開 GCP 帳號、重做一套部署，
     大概五到八小時，但 Tier 不會因此提高。
     我把時間放在把關 4 的零停機實測做扎實。
     評估過程寫在報告裡。」

 已經 push 出去了，想退回原狀（明天最可能用到的救命指令）
   → 貼：

git revert --no-edit HEAD && git push origin main

   → 它會走一次完整流水線，約 1 分半後 EC2 退回，ECS 再等 3 分鐘
   → 這不是特殊程序，就是「再部署一次」，跟正常上線走同一條路

   → 它會把折扣退回 6 折、把警語拿掉，然後從第 2 步重來

   → 貼：bash 現場還原.sh
   → 它會印出目前的折扣與手續費，看一眼就知道
