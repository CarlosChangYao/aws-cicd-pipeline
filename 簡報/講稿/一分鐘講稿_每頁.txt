─────────────────────────────────────────
 第 1 頁 · 封面
─────────────────────────────────────────

「各位老師、各位同學好，我是張博堯。

我的題目是 P3，CI/CD 演化闖關，做到 Tier 3。

用一句話說明我做了什麼：

我把『改一行程式碼到它上線』這件事，
從 18 個步驟、16 分鐘的人工作業，
變成 1 個步驟、80 秒的全自動流程。

這裡的每一個數字都是我實際測出來、有截圖佐證的，
不是估算，也不是抄來的。

我的程式碼、設定檔、還有每一關的紀錄，
全部在 GitHub 上這個網址，是公開的，各位隨時可以查。

等一下講完，我會現場示範一次給大家看。」


─────────────────────────────────────────
 第 2 頁 · 專題全貌：六關演進
─────────────────────────────────────────

「這是整個專題的架構。

我不是一開始就做出自動化，而是分成六關，一關一關往上疊。
每一關都是在解決前一關留下來的一個具體問題。

關 0，全部手動做一次，目的是體會痛點、建立基準線。
關 1，容器化，解決『環境不一致』。
關 2，自動建置，解決『打包靠人記得』。
關 3，自動部署，解決『上線靠人動手』。
關 4，滾動更新，解決『換版會斷線』。
關 5 是跨雲，我評估之後決定不做，理由等一下會說明。

我想強調的是這個順序本身。

如果我一開始就直接做自動化，我不會知道它到底省了什麼。
先痛過一次，後面每一個數字才有比較基準。」


─────────────────────────────────────────
 第 3 頁 · 關 0：手動部署，建立基準線
─────────────────────────────────────────

「先講關 0。

這一關的目標不是『部署成功』，而是『記錄部署有多痛』。

我完全用手動的方式，把程式放到伺服器上跑起來。
結果是 18 個步驟、16 分鐘，中間失敗了 2 次。

失敗的原因很具體：一次是程式碼用貼的貼進去，貼壞了；
一次是套件裝到錯的地方。

但最關鍵的問題不是慢，是這個——

手動部署完之後，我沒辦法回答『線上跑的到底是哪一版』。
網頁上那一格我只能填『none-manual-deploy』，因為我真的不知道。

這一頁的每個數字都是靠截圖時間戳算出來的。
後面五關所有的改善，都是拿這一頁當基準。」


─────────────────────────────────────────
 第 4 頁 · 關 1：容器化 + ECR         【時間不夠可壓成半分鐘】
─────────────────────────────────────────

「關 1 解決的是環境問題。

左邊是關 0 的做法：程式碼用貼的，目標機器要先裝 Python，
要自己建虛擬環境、自己裝套件。換一台機器，全部重來一次。

右邊是關 1：我把程式跟它需要的整個環境，
一起打包成一個映像檔，放到 AWS 的 ECR 倉庫。

之後要部署，就是一個 docker pull，完整傳輸不會壞，
Python 跟套件都已經在裡面了。

這解決了工程上最常見的一句話——
『在我電腦上明明可以跑』。

因為現在跑的不是『你的電腦』，是那個映像檔，
而映像檔在哪一台機器上都長一模一樣。」

【壓縮版】
「關 1 是把程式跟它的執行環境一起打包成映像檔。
 這樣就不會有『在我電腦上明明可以跑』的問題，
 因為在哪台機器上，跑的都是同一個映像檔。」


─────────────────────────────────────────
 第 5 頁 · 關 2：自動建置，測試不過不准上線
─────────────────────────────────────────

「關 2 開始進入自動化。

流程是這樣：我 git push，這是唯一的人工動作。
接下來 GitHub Actions 自己跑測試、自己打包、自己推到 ECR。

這裡最重要的是第二步——測試。

我在流水線裡設了一個相依關係：測試沒過，後面三個階段完全不執行。
不是『警告一下還是讓它過』，是直接停住。

這件事我實際演練過。我故意把測試改壞、推上去，
結果是測試紅燈，後面三個階段全部標成 skipped，
線上版本完全沒動，連映像檔倉庫都沒有新東西進去。

用技術的話講，這叫持續整合的品質閘門。
但如果用金融業的語言講，這是自動化的內控關卡——
以前靠人簽核、靠人記得檢查，現在是機器強制執行，繞不過去。」


─────────────────────────────────────────
 第 6 頁 · 關 3：改一行程式碼，80 秒自動上線
─────────────────────────────────────────

「關 3 是這個專題的核心。

這是我實際測到的時間軸：

14 點 22 分 49 秒，我 git push，這是唯一的人工動作。
接下來機器自己跑測試、建置映像檔、推到 ECR、
再透過 AWS 的 Systems Manager 部署到伺服器。

14 點 24 分 09 秒，線上版本自動更新完成。

總共 80 秒。中間我沒有做任何事。

跟關 0 對照：18 個步驟變成 1 個，16 分鐘變成 80 秒。

還有一件更重要的事——
現在網頁上會顯示這次部署對應的 commit 編號，
跟我電腦裡的完全一樣。

也就是說，『線上跑的是哪一版程式碼』這個問題，
從關 0 的『不知道』，變成關 3 的『百分之百確定』。」


─────────────────────────────────────────
 第 7 頁 · 關 4：滾動更新，換版不中斷      【時間不夠可壓成半分鐘】
─────────────────────────────────────────

「關 3 還留下一個問題。

它的部署方式是先殺掉舊容器，再啟動新容器。
中間那幾秒，服務是斷的。單機只有一個容器，殺掉就沒了。

關 4 用 ECS Fargate 加負載平衡器解決這件事。

做法是：先啟動新任務，暫時擴充到 200%，
等新任務通過健康檢查，確認真的活著，才逐一終止舊任務。

我在設定裡寫了兩個數字：健康的比例不准低於 100%，
但可以暫時衝到 200%。翻成白話就是——
可以多請人，但不准先開除人。

我實測過：部署進行的同時，我對外打了 300 次請求，
300 次全部成功，可用率 100%。

在金融業，這對應到的是盤中能不能上線。
服務不會斷，才有可能在交易時間內做調整。」

【壓縮版】
「關 4 解決換版會斷線的問題。
 做法是先開新的、確認健康了，才關掉舊的，中間永遠有人在服務。
 我實測部署期間打 300 次請求，300 次全部成功。」


─────────────────────────────────────────
 第 8 頁 · 成果：用數字說話
─────────────────────────────────────────

「這一頁是整份專題最重要的一頁。

左邊到右邊，是關 0 到關 4 的對照：

步驟數，從 18 步變成 1 步。
耗時，從 16 分鐘變成 80 秒。
人工介入，從每次都要，變成零。
失敗次數，從 2 次變成 0 次。
換版中斷，從會斷，變成完全不斷。

還有一項沒有辦法用數字表達，但我覺得最重要——

線上跑的是哪一版，從『不知道』變成『查得到』。

前面四項是效率，最後一項是風險。
對金融業來說，後者的價值比前者高。」


─────────────────────────────────────────
 第 9 頁 · 安全設計：零長期憑證          【時間不夠可壓成半分鐘】
─────────────────────────────────────────

「這一頁講安全設計。

整條流水線，沒有任何一組長期有效的密碼或金鑰。

GitHub 要存取 AWS，用的是 OIDC，
每次執行時去換一張一小時就過期的臨時憑證。
所以就算 GitHub 帳號被入侵，對方也拿不到能長期使用的東西。

部署到伺服器也不是用 SSH。
那台機器沒有建金鑰對，防火牆連 22 port 都沒開，
我還把 sshd 服務整個停掉。三層都堵死。

部署是靠 AWS 的 Systems Manager，
由機器主動向外拿指令，而不是外面連進來。

在金融業，金鑰外流跟特權帳號被盜用，
是稽核最常問的兩件事。
這個做法不是把鑰匙管好，是根本沒有鑰匙。」

【壓縮版】
「整條流水線沒有任何長期金鑰。
 GitHub 跟 AWS 之間用 OIDC 換一小時就過期的臨時憑證；
 伺服器沒有金鑰對、22 port 沒開、sshd 也關掉了。
 不是把鑰匙管好，是根本沒有鑰匙。」


─────────────────────────────────────────
 第 10 頁 · 延伸應用：這解決什麼問題
─────────────────────────────────────────

「講到這裡，我想回答一個問題：這套東西實務上有什麼用。

我自己在金融業工作，所以我用券商的角度來看。

在金融業，『系統上線』不是技術問題，是風險與法遵問題。

手動部署 18 個步驟，仰賴人不出錯——這叫作業風險。
不知道線上是哪一版——稽核會問可追溯性。
出事要復原得重跑整套流程——這是營運持續的問題。
上線只能收盤後——法遵要求的回應時效做不到。

右邊這一欄是我的解法，每一條都對得上左邊。

我想強調的是：這條流水線的價值不只是快。
是把作業風險、稽核軌跡、復原時間，一起處理掉。

接下來我現場示範一次，各位就會明白我的意思。」

 第 12 頁 · Demo 中：AWS 上自己長出新版本
─────────────────────────────────────────

「這兩張是 AWS 映像檔倉庫的前後對照。

左邊是我 push 之前，最上面是 v1.2.41。
右邊是 push 之後大約一分鐘，最上面多出了 v1.2.42。

我要強調的是——我從按下送出到這張截圖為止，
完全沒有登入 AWS，沒有點任何按鈕。
這個新版本是流水線自己推上去的。

還有一個細節值得看：
每一列都掛著版本號跟一串 commit 編號。
latest 這個標籤會被下一次建置搶走，
但 commit 編號永遠釘在原地。

所以萬一這次改錯要退回去，指定的就是這一串。」

 第 13 頁 · Demo 後：風控警戒生效
─────────────────────────────────────────

「這是上線之後的畫面。

單筆委託上限從 50 萬變成 10 萬，
顏色從藍色變成紅色，旁邊出現『風控加強中』的標籤，
整張卡片的外框也變紅了。

請注意：我只改了一個數字。

這三個變化不是我改了三段文字，
是程式自己判斷『現行上限低於平時水準』，
所以整個頁面進入警戒狀態。這是邏輯，不是文案。

從我按下送出，到這個畫面出現，不到兩分鐘。

如果用傳統的手動流程，這件事要開變更單、跑簽核、
排收盤後的上線窗口，最快是隔天。

中間那幾個小時，風險是敞著的。

這就是這條流水線在金融業真正的價值。」
